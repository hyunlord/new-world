# ADR 0066 — M3D-1: a second, 3D view of the colony beside the 2D renderer

## Date
2026-11-15

## Source
Owner decision 2026-11-14 (planner goal `GOAL_3D.md`, M3D-1): switch the view to 3D now so buildings get height, roofs,
materials, light and a cutaway. Supersedes the 2026-11-07 decision to keep a 2D view with depth until after M-GROW.
Builds on ADR 0033 (kinds are data), ADR 0034 (the 2D renderer) and ADR 0016 (C2: the view never changes the sim).

## Context
Buildings in the 2D view are flat rings of wall tiles. The simulation already holds everything a 3D house needs — the
wall grid with materials and styles, rooms with a roofed flag, template sites with era and roof style, workshops by
blueprint construction style, appearance per person — but no 3D view existed, and the 2D view must stay the default
until the owner approves parity.

## Decision
- A second renderer, `scenes/world3d/World3D.tscn` + `scripts/world3d/*.gd`, is added under `Main` when
  `--renderer=3d` (or the `renderer_3d` interface setting) asks for it; the 2D `ColonyView` stays in the tree, hidden.
  Its purely visual layers (ground, plants, trees, buildings, outcrops, livestock) stop processing; people, animals,
  rooms and OrderTool keep running because the unchanged order and click code hit-tests through them.
- The Camera2D stays the single view state. `camera_rig.gd` follows it (1 tile = 1 unit; 30° FOV; 50° pitch; a tile
  ≈ 64·zoom px at the target; five zoom steps; Q/E turns 90°, and the 2D camera's `screen_rotation` keeps pans
  screen-relative).
- Screen ↔ world conversion goes through `scripts/world/view_projection.gd`: the canvas transform in 2D, a terrain ray
  (roof planes first; people and animals by their projected bodies, answered with their 2D drawn-rect centre) in 3D.
  OrderTool, the camera's zoom anchor and the panels that pin to the map use it, so every order and panel works in
  both views without a 3D copy of their logic.
- All models come from deterministic Blender scripts (`tools/3d/blender/*.py`, `blender -b -P build_all.py`,
  byte-identical reruns) into `assets/3d/models` and `assets/3d/vat`. Every identity → model/colour mapping is data
  (`assets/3d/bindings3d.json`, by the identities the bridge already sends: species, construction style, art shape,
  tint material, animal id, wall style, era), every tunable is in `assets/3d/params3d.json`, and each family has a
  fallback. Walls, doors, fences, floors and roofs are generated procedurally from `get_space` and `get_rooms`.
- Crowds are vertex-animation-texture MultiMeshes (positions per unsplit vertex, float16, flat normals from screen
  derivatives); there is no per-person node. Map overlays and order feedback are one texel per tile projected on the
  terrain and on plants.
- No Rust change and no new bridge getter: every read the 3D view needs already existed.

## Alternatives considered
- Draw the 3D view in its own SubViewport with its own input code: duplicates OrderTool, the inspector clicks and the
  drag logic, and drifts from 2D. Rejected for the shared projection hook.
- Replace the 2D renderer now: rejected; the goal keeps 2D the default until the owner approves parity.
- AnimationPlayer per person: 500+ skeletons per frame and per-person nodes. Rejected for VAT crowds.
- Reuse the 2D pixel textures on 3D walls: blurry or pixelated at 3D scale. Rejected for procedural profiles coloured
  by material.

## Consequences
- The 2D view's own drawing (ghosts, labels, mood badges) does not appear in 3D; the order feedback is redrawn as
  tile overlays. Text labels on the map (site progress, hover names) are an M3D-2 gap.
- People and animals are one placeholder model per species family until M3D-2's character models.
- Hit-tests still depend on the hidden 2D AgentLayer/AnimalLayer positions; retiring 2D needs those moved first.
- The 3D view reads heavy snapshots only when the colony versions or the tick move (a per-frame `get_trees` read alone
  cost ~6.5 ms once no 2D layer shared the frame cache).
