Autonomous decisions of the WM-1 run (GOAL.md 0.3.1), newest last. Each: what, why.

## Part 0

- **D0.1 Shared ssh config.** The Mac reaches the DGX with a throwaway `ssh -F` config in the session scratchpad (`Host dgx` → `hyunlord@100.70.109.50`, ControlMaster); `~/.ssh/config` untouched.
- **D0.2 Both branches created at `ce7acb25`.** `codex/worldmodel-2026-10` was pushed at `ce7acb25` (unchanged base) so it can later move by fast-forward only.
- **D0.3 Python environment: venv + PyTorch cu130, but CUDA unusable → Grace CPU.** The system interpreter (Python 3.12.3) has no torch. The venv `/home/hyunlord/work/wm1-venv` installed `torch 2.14.1+cu130` and `numpy 2.5.2` from the official cu130 index (wheel found, so cu129/cu128 were not tried). Creating a CUDA context fails at the driver level: `cuDevicePrimaryCtxRetain` and `cuCtxCreate` return 2 (`CUDA_ERROR_OUT_OF_MEMORY`) through plain `ctypes` against `libcuda.so.1`, with 7–16 GB `MemFree`, ~95 GB `MemAvailable`, no cgroup memory limit, no ollama model loaded. The only visible GPU user is another user service (`ht-estate` embed server), which this run must not stop; dropping the page cache needs root (no sudo). A docker NVIDIA container (1.3 step 3) uses the same driver and would fail the same way, so the run falls back to 1.3 step 4: **training on the Grace CPU** with this venv's torch (`torch.set_num_threads(16)`), and every run's `config.json` records the device. CUDA is re-checked before Part 2 training; if it works then, the device of every run is still recorded and the W7 rerun uses the main run's device.

## Part 1

- **D1.1 Batched predictor interface.** The harness accepts `StepPredictor.step(history, ctx) -> next V row` (persistence and daily naive use it) and a batched `rollout(ep, starts, horizon, actions)`; the GRU and the ridge implement the batched form because T1 and T2-any need tens of thousands of rollouts. A unit test checks the step and batched forms agree (daily naive) and that no predictor reads rows after its start.
- **D1.2 Ridge rollout vectorized over starts.** `RidgePredictor.rollout` reproduces `bench_v0.rollout` (lags from a 24-row buffer, severity held at the start row, calendar from the episode, last-24-hour action sums) for many starts at once; W1 compares it with `bench_v0.json`.
- **D1.3 `rain_ticks_left` is reduced with max, the stocks and members with sum** (one settlement in every v0 episode, so the choice does not change any value); the presence flag is "the settlement row is not NaN".
- **D1.4 Action scaling.** Requested amounts are divided by the largest amount of the kind's B_act grid (food 120, wood 80, rain 24, cold snap 3, windfall 40): fixed constants, not fitted on any data.
- **D1.5 Fire in V predictions.** A model's `fire_lit` in a predicted V row is its Bernoulli head thresholded at 0.5 (MAE-optimal for a binary target); T3 uses the probability; T3b counts thresholded dark 02:00 rows.
- **D1.6 T2-any start set.** Every hour 00:00–23:00 of the bench's start days 3, 10, 17, … whose horizon fits, with the bench's denominator; breakdowns by target season, target-row severity and start hour.
- **D1.7 T3b.** Cases: 06:00 of one-based days 24, 52, 80, … (each winter's third day) whose fifth night ends inside the episode; truth: the number of dark 02:00 rows after the evenings of that day and the next four. Ridge features exactly as GOAL 7.4 (wood at 06:00, deadwood total, the wood drop 18:00→06:00 of the two previous nights, the deadwood change 06:00→06:00 of the two previous days, members), λ from the bench's grid on A val (MAE of predictions clipped to [0, 5]); baselines fit on A train. Splits: A test (W4), B test, OOD_v12 (no oracle, severity −1), OOD_long.
- **D1.8 T4 branches.** Both branches start from the factual episode's row at the intervention tick (the harness checks that the variant's rows ≤ that tick equal the factual's), with actions = the intervention at that row or none; c_cf_targets reads the factual rows ≤ the tick and the predicted rows after it. Cold member-hours and deaths are reconstructed from the predicted hourly differences of the cumulative tallies, starting from the factual value at the tick.
- **D1.9 T5 scored rows.** Every row t in 23 … T−2 and agent alive at t−23, t and t+1 (so the 24-hours-earlier baseline is defined); needs nMAE denominator = std of the split's scored targets.

## Part 2

- **D2.1 Training runs concurrently on the CPU.** Two to four jobs at 8 threads each share the Grace CPU (other users' load 4–11); `--threads` is recorded in every config, and the W7 rerun uses the same thread count as the run it reproduces.
- **D2.2 Recipe r1 → r2 (strike 1 on W2 and T1).** M1 main r1 (`m1gru_main_s0`, GOAL's recipe: windows of 168, k 1→24) beats persistence at 24 h on val (T2-24 0.115 vs 0.130) but drifts at 168 h (val T2-168 0.84 vs persistence 0.53: `fire_lit` and `food_on_bushes_total` reach nMAE 1.0, `wood_stock` 1.49) and loses on T1 (val 0.113 vs the ridge's ≈ 0.100; `adults_working` 0.56, `food_on_bushes_total` 0.23). Hypotheses: (1) the rollout loss never unrolls past 24 steps and starts from short contexts (j uniform in the 168-row window), so 168-step rollouts leave the training distribution; (2) the Gaussian NLL down-weights high-variance changes, which is not what an MAE metric rewards. Recipe r2: windows of 336 rows, k 1→168 over the first half, rollout starts only after a full 168-row context (`roll_min_context` 167, as in evaluation), 2 rollout starts per window, an L1 term on the predicted mean change (`tf_l1` 1.0) added to the NLL, and features that are never negative in train clamped at 0 in rollouts (`clamp_nonneg`). Early stopping, optimizer, heads and architecture unchanged. r1's runs keep their test evaluation (they are listed configurations) and are reported.
- **D2.3 r2 step budget fixed before any r2 result.** At k = 168 a step costs ≈ 1 s of one core, and with eight jobs plus other users' load (≈ 33 on 20 cores) the first r2 launch (18:47–18:58) would have hit the 2-hour wall-clock cap at a load-dependent step — making the stop point, and so the W7 same-seed rerun, nondeterministic. Those runs were stopped (moved to `wm1-runs/_aborted/`, never evaluated) and relaunched with `max_steps` 5000 and `eval_every` 250 (the curriculum reaches k = 168 at step 2,500; patience 5 evaluations = 1,250 steps). This is part of r2, not a new recipe (no r2 number existed). M3 was paused (its first launch also moved to `_aborted/`) and is relaunched when the GRU jobs finish.
- **D2.4 r2 step budget tightened again before any r2 result.** Measured step cost under the shared load: ≈ 0.45 s + 0.008 s × k (0.86 s at k = 51), i.e. ≈ 1.8 s at k = 168, so 5,000 steps would need ≈ 7,300 s — over the 2-hour cap. The 5,000-step runs (stopped at step ≈ 800, moved to `_aborted/r2_5000/`, never evaluated) were relaunched with `max_steps` 4000 and `eval_every` 200 (≈ 5,800 s estimated; k reaches 168 at step 2,000; patience 5 = 1,000 steps). The two seed-0 runs had matched exactly up to step 750 (val 0.1937, 0.1682, 0.1565 at steps 250, 500, 750), so the training loop is deterministic on this CPU.
