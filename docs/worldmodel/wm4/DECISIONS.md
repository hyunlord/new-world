## Part 1
- **L1.1 Families recorded world by world.** `--fork-tick` is per recorder call, and every val / test world has its own c_w, so each family is one call (`--seeds s..s+1 --fork-tick c_w --replicates 1 --schedule-dir obs/schedules/fam/s<seed>/ --include-factual`); `obs/schedules/fam/s<seed>/ref.json` (c_w, the cast) sits beside the three schedule files and is not read by the recorder (it reads only `s*.json`).
- **L1.2 Manifest.** `obs_manifest.json` paths are relative to `WM_DATA_ROOT` (`obs/…`), as `wm1.data.load_split` reads them; `schedule_id` is `obs` for a casting world's observed episode and `none` otherwise; the family members carry `obsfam_<id>` with `none` included (`obsfam_none`). The test worlds' observed episodes are not in any split (no group reads them).
- **L1.3 Checks beyond GOAL.md 6.2.** `fam-check` also asserts that a family's `none_r0` equals the world's factual episode and that a casting world's observed `_obs` episode equals its family member of the same arm, both by per-array sha256 (the fork with replicate 0 is a no-op), and that every family member's single record has the arm's kind, amount and tick c_w.

## Part 2
- **L2.1 Control units on decision rows only.** GOAL.md 7.2's control set is C = {(k, c): k cast at no decision row j < c + h}; a unit (k, c) also needs c to be a decision row of k (alive, a settlement), because the treated are drawn only there (positivity; with p = 0 at c a dead world would enter the control mean with no treated counterpart). No world of the obs split has a non-decision row in days 8 … 60 (policy summary `non_decision_rows` 0), so this changes nothing on this data.
- **L2.2 Baselines' split shift.** `naive`, `ipw` and `match5` predict the restricted split-day shift by the same construction on the restricted split day from c (controls of h = 720). The shift is reported, never judged (12 cells per lag). Caveat (review round 1): a control of h = 720 may cast after c + 720 and before its split, so its restricted split day can reflect that later cast.
- **L2.3 CRN / CT epochs.** The authors' epoch counts are for 10,000 training sequences; WM-4's 400 (obs) would give 450 CT optimizer steps. Epochs are scaled to the authors' number of optimizer steps (METHODS.md D7), each run capped by its time budget.
- **L2.4 CRN / CT checkpoint selection and the grid.** The best validation-factual-loss epoch is kept (METHODS.md D8); the grid's chosen member is the method's `_obs_s0` run itself (no retraining), so the grid's time is the s0 run's time (4 × 20 min ≤ GOAL.md's 1.5 h).

- **L2.5 Dry runs read val families (review round 1).** `dryrun.sh` (01:56–02:04, before part b) evaluated a 120-s CRN, a 120-s CT and `wm2_m1bact_v19_s0` on the val families' counterfactual members, which GOAL.md 4.3 reserves for baseline selection. Their only use was to exercise the code paths; no selection read them: `GRID` and `DEFAULTS` are unchanged since `19608337` (23:39), and the one change after the dry runs (`039e480c`) set the validation start tokens and evaluation timing from the timing measured, not from any effect number. The last dry run (`_dry/m1obs`, 3 M1b-obs steps on train / val) ended at 02:16:51, 20 s after the part-b commit (02:16:31); it read no test data (review round 2, MINOR 5).

## Part 4
- **L4.1 One queue.** `wm4/_setup/queue.sh` runs every training (and every cost check) one at a time from `queue.txt` lines `RUN SHA BUDGET CMD`, re-read before each run; when no line is pending it waits, so lines are appended as their code and data exist. Test evaluations are never launched by the queue (they wait for METRICS.md part b, `finals4.sh`).
- **L4.2 Hazard recalibration ran beside the first ablation run.** The three Platt fits (9.4) are 745 frozen-trunk 720-step rollouts each plus two val calibrations (≈ 80 s per seed), an evaluation-sized GPU job, run at 23:28–23:32 beside `wm3_ctrl_s1` rather than queued behind four trainings (train and val data only). All three were kept (val Brier below the original's): a, b = 0.927, −2.892 (s0); 1.504, 1.243 (s1); 1.505, 1.636 (s2); val Brier 0.576 → 0.247, 0.444 → 0.242, 0.357 → 0.237 (val climatology 0.242; train climatology 0.216, train after 0.212–0.215).
- **L4.3 CUDA contexts under memory pressure.** On the GB10 (unified memory) a second CUDA process could not create its context at 00:36 while other users' jobs left 2.3 GiB free (46 GiB in page cache, swap full); the running training was unaffected. GPU jobs beside a training (evaluations) are retried when this happens; a failure of this kind is environmental and recorded, not a result.
- **L4.4 CT under its pre-registered time budget.** The cost check (GPU alone) measured ≈ 0.83 s per CT optimizer step, so a 1,200-s grid member runs ≈ 1,400 of the authors' 11,850 steps (the kept CT-obs checkpoint: 477, METHODS D14) and a 2,400-s v2 run ≈ 2,800. The budgets of METRICS.md part b are kept (they were fixed before any number; changing them after the cost check would be tuning on cost); CT's undertraining relative to the authors' step count is a limitation reported in WM4.md, not corrected. The implementation was not optimized after part b (the vendored attention re-builds its relative-position index on the CPU at every call; a faster version would change the code that produced the pre-registered runs).
