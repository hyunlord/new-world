최종 측정은 두 배율에서 각각 310초 캡처를 완료했다. 첫 10초 이후 50 ms 초과 0회, 분당 33 ms 초과 3회 이하라는 기준을 유지한다. 원시 캡처의 완료·계측 상태와 오류 목록은 정상이나, wrapper 영수증은 기준 실패에 따라 complete false / exit 1이다. 어느 기록도 지우거나 성공으로 바꾸지 않는다.

`reviews/final-stall1-analysis.md`에 따르면 ½×의 1초 지연은 시작 후 12.421–13.429초에 발생했다. 대부분이 pre-draw→post-draw 구간에 있으며 측정된 Rust나 지면 준비 시간으로 설명되지 않는다. 첫 배율의 큰 보고서를 두 번째 배율 실행 중 읽은 호스트 작업은 **오염 후보**지만 시간 기준이 달라 직접적인 원인으로 확정하지 못했다. 이를 제품의 1초 회귀로 단정하거나 채점에서 제외하지 않는다.

마지막 분의 초과 프레임 6개는 이 초기 이상치와 독립적으로 빈도 기준을 위반한다. 해당 프레임의 지면 처리는 약 13–14 ms, 그중 `GroundLayer._update_trees`는 약 10–11 ms였다. 다른 처리와 스케줄링 지연도 포함되므로 나무 갱신만으로 전체 지연을 설명하지 않는다. 후속 측정은 두 배율이 모두 끝날 때까지 보고서를 읽거나 출력하지 않는 격리 조건이 필요하다. 기존 FAIL은 보존한다.

조명 준비는 실제 shader receiver로 검증했지만 특정 드라이버의 shader compile이 유일한 원인이라고 단정하지 않는다. 오래된 `last_bake`나 누적 최악값을 현재 프레임으로 세지 않고 실제 추가된 bake event로 구간을 나눈다.


트리 변환 후보는 같은 이름의 GString 변환을 재사용하며 native 2검사와 실제 Godot 22검사에서 전체 사전 일치를 확인했다. 고유 변환 횟수의 정방향·역방향 실패 대조군과 최초 컴파일·서식 실패를 보존했다. 후보는 유지하되 실제 끊김 개선은 아직 측정하지 않았으며 stall2는 대기다. 되돌림 후 Python 73검사(16.741초)와 기존 전체 oracle·실제 tree probe는 PASS다. 이 결과로 최신 소스의 전체 Rust 시험이나 전체 게이트를 대신하지 않는다.

ISS330 수정은 `frame_post_draw`를 주 계수로 쓰고 Engine 계수와 비교하며 창 상태를 기록한다. windowed/topmost 조건에서 FPS8과 FPS9의 두 렌더 계수가 일치했다. `force_draw`나 process-frame FPS로 대체하지 않았고 측정 시간과 기준도 유지했다. 캡처 과정의 수정은 FPS 성능 성공과 별개다.
